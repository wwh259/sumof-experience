# 抽取规则

目标：一次对话或文件里通常只有 15% 的内容值得留下。任务是识别这 15%，而不是压缩全篇。

## 1. 只采 5 类

| 类型 | `type` 值 | 判据 | 反例（不采） |
|---|---|---|---|
| 决策 | `decision` | 有多个可行选项，最终选了一个，且有理由 | 唯一的实现方式 |
| 坑 | `pitfall` | 表面现象与真实根因不一致，会复发 | 一次性的环境故障 |
| 模式 | `pattern` | 同样做法能在 ≥2 个场景复用 | 只适用于当前文件的写法 |
| 约束 | `constraint` | 硬性红线、上限、版本限制、平台限制 | 可随意调整的偏好 |
| 有效路径 | `path` | 在信息不足时被验证有效的问题定位顺序 | 试错过程中的无效尝试（进「失败与反例」） |

## 2. 直接丢弃

- 寒暄、确认、进度汇报
- 需求复述、背景介绍、方案罗列
- 一次性的机器差异、网络抖动、路径拼写
- 可从代码、配置、文档原文直接读到的内容
- 没有验证的推测（除非标 `confidence: 0.3` 且注明「待验证」）
- 同一结论的第二次表述
- 含本机绝对路径（`D:\`、`C:\`、`/Users/`、`/home/`、`/mnt/` 等）的任何写法——**证据字段同样禁止**；一律改写为「项目名 + 相对路径」，如 `qwen_deploy/.env`

## 3. 五问筛选

对每个候选依次回答，任一答不上来即丢弃：

1. 下次遇到什么信号时应该想起这条？
2. 照这条做，具体动作是什么？
3. 为什么有效？说不出机理的，降级为 0.3。
4. 证据是什么？复现次数、报错原文、文件路径、对话轮次，至少一项。
5. 什么时候不成立？

## 4. 证据分级

| 级别 | 证据形态 | 置信度上限 |
|---|---|---|
| A | 复现 ≥3 次，或官方文档/源码明确 | 0.9 |
| B | 复现 2 次，或单次但有完整日志/报错原文 | 0.8 |
| C | 单次成功，无对照 | 0.6 |
| D | 推理得出，未验证 | 0.3 + 标注待验证 |

## 5. 归并

- 多个现象同一根因 → 合并为一条，证据写「N 次不同表现」并列出表现
- 同场景不同做法 → 保留一条，把被否的方案写进「失败与反例」
- 一个结论依赖另一个结论 → 合并为一条，做法内写顺序
- 合并后仍无法用 8 行表达 → 说明主题过大，按拆分规则处理

## 6. 冲突处理

与已有经验卡冲突时：

- 旧卡正文、证据、坐标一律不改
- 新建一张卡，`supersedes` 填旧卡 id；旧卡仅允许改 `status: superseded` 与 `superseded_by`
- 无法判断谁对：两张都保持 `active`，`related` 互指，由知识库层裁决
- 需要补充而非否定：新建卡 `related` 指向原卡，不改原卡
- 影响面大时在「复用清单」加一条待裁决动作

## 7. 写作语气

- 动词开头，陈述句，单句单义
- 保留原文数字、版本、参数、路径
- 每条经验自包含，不依赖上下文顺序阅读
- 「做法」必须能被一个不了解背景的人直接执行
